# 快速专家审查（`~tune` 执行手册）

这是 Skill Gardener 的**第一入口**,零数据、一轮出结果。它对标的不是 ML 实验,而是一位资深 skill 作者拿你的 SKILL.md 从头读到尾、当场指出硬伤并改好的那种审查——这是实践中性价比最高的 skill 改进方式,不需要日志、锚点、竞技场。

**什么时候用**:几乎总是先用它。日志再多的 skill,第一轮也应该先做静态审查——很多问题(路径错、触发词差、结构 bug、与时俱进缺口)根本不需要数据就能看出来,先修掉这些再谈需要数据的深度培育。

**与深度培育的关系**:`~tune` 是快速档,一轮内完成"读→诊断→在副本上改→给 before/after"。`~cultivate`(见 SKILL.md)是深度档,当你有真实日志、且静态问题已修完、还想继续压榨质量时才走。多数 skill 在 `~tune` 之后就已经明显更好了。

---

## 工作流程(一轮完成,不需要子 agent)

### 第 1 步 · 安全落点

不依赖 git 仓库。把目标 skill 复制一份到 `<skill>.gardener-draft/`(或同目录下带时间戳的副本),所有改动在副本上做,原文件不动。最后给用户 before/after,由用户决定是否覆盖原文件。若目录恰好在 git 下,顺带建 `gardener/<skill>/<date>` 分支更好,但**不是前提**。

### 第 2 步 · 通读 + 六维静态诊断

完整读 SKILL.md 及其引用文件,按下面六个维度逐条过。每个维度先给结论(有问题/无问题),有问题就引证据(引用具体行/段)。

#### 维度 1 · 触发与描述(description)

description 是 skill 唯一的触发机制,也是最高频的失效点。检查:
- **触发覆盖**:真实用户会怎么说?那些说法都能触发吗?口语、简写、别名、场景化说法有没有覆盖?
- **过触发/欠触发**:description 是否过宽(蹭到无关场景)或过窄(该触发时不触发)?近义边界 skill 会不会抢?
- **是否"推"得够**:Claude 倾向于欠触发。description 要主动列出"当用户说 X / 提到 Y / 抱怨 Z 时触发",而不是只描述功能。

#### 维度 2 · 结构完整性(本类问题最隐蔽、危害最大)

这类 bug 会让 skill 的部分设计**根本不生效**,静态审查最该抓的就是它们:
- **配置/文件是否在会被加载的位置**?主配置放在非自动加载路径(如 `.claude/CLAUDE.md` 而非项目根 `CLAUDE.md`)、skill 放在非标准目录 → 启动时可能没加载。
- **子 agent 是否有 YAML frontmatter**(name/description/tools)?`.claude/agents/` 下缺 frontmatter 的文件不会被注册成可调用子代理,"自动质检/自动调度"会静默落空。
- **引用路径是否都存在且正确**?SKILL.md 引用的 references/scripts/agents 文件是否真实存在、路径是否对?(逐个核对,这是高频低级错误)
- **命令/指令表与正文是否一致**?正文描述的指令、文件名,和指令表、文件树对得上吗?
- **双引擎**:如果是需要自动加载配置的 agent 型 skill,有没有 Codex 的 `AGENTS.md`?(纯 skill 靠 description 触发则无需)

#### 维度 3 · 指令质量(rules vs examples)

- **示例优先于规则**:关键行为是靠"一条抽象规则"还是"一个完整示例"传达的?规则常被忽略,一个完整的 input→output 示例胜过五条规则。缺示例的关键环节标出来。
- **规则疲劳**:是不是堆了太多 MUST/NEVER?过多硬规则互相打架、且钝化模型判断。能不能把"为什么"讲清楚、让模型自己判断,替代一条生硬的禁令?
- **自相矛盾**:规则和示例有没有打架?(模型跟示例走,不跟被违反的规则走)
- **过度约束 vs 欠约束**:输出是不是被模板锁死到僵硬(B4),或松到每次都不一样(B3)?

#### 维度 4 · 与时俱进(内容是否过期/脱节)

- **陈旧假设**:引用了过时的模型名、废弃 API、改过的路径、变化了的平台规则?(这是本 session 反复出现的高频问题——如平台政策、工具命令改名、版本号)
- **缺失的实用模块**:对照这个 skill 的真实使用场景,有没有明显该有却没有的能力?(如:面向投稿的写作 skill 却没有投稿交付;面向发布的 skill 却没有合规自查;涉及生成的 skill 却没有翻车修复回路)
- 需要联网核实的事实(平台规则、版本、价格),不凭记忆改——`~tune` 允许联网。

#### 维度 5 · 篇幅与渐进披露

- SKILL.md 是否过长(理想 <500 行)?过长就该把细节下沉到 references/,正文留指针。
- 反过来,是否该内联的关键示例被藏进了引用文件、导致主流程不完整?
- Token 经济:有没有空洞的、不产生行为的段落可以删?

#### 维度 6 · 小白可用性 / 上手门槛

- 一个第一次用的人,知道怎么开始吗?第一步清晰吗?
- 前置条件(要装什么、要准备什么数据)有没有说清、门槛是否过高?
- 有没有随包的使用说明?

### 第 3 步 · 输出诊断 + 分级修复

按"频率 × 严重度"排序,给一份诊断清单。每条标:
- **🔴 必修**:结构 bug、路径错、触发失效、事实过期——这些不需要数据就能确认,直接在副本上改。
- **🟡 建议**:质量提升(补示例、去规则疲劳、补实用模块)——在副本上改,但说明取舍。
- **🔵 需数据**:凡是"哪个措辞更好""风格保真度""输出稳定性"这类需要在真实使用上验证的,**不在快速档硬改**,标记为"建议走 `~cultivate` 深度档,前提是你有日志"。

诚实分流:能静态确认的当场修,需要经验证据的老实说"这个我不该拍脑袋,要么你给我几个真实例子(回溯档),要么记一段日志再深度培育"。

### 第 4 步 · before/after 交付

- 展示改了哪些、每处**为什么更好**(结论先行,证据在后)
- 给一份**变更说明**(changelog)——这既是交付物,也进入健康档案(见 `health-card.md`)
- 副本保留,用户确认后再覆盖原文件
- 如果用户要按自己的方式发布(如打包 .zip + 使用手册),照做

## 快速档的诚实边界

`~tune` 能可靠解决的:结构 bug、路径/引用错误、触发词、事实过期、缺示例、规则疲劳、篇幅、上手门槛、明显的实用模块缺口。这些占真实 skill 问题的大多数,且都不需要数据。

`~tune` **不**假装能解决的:两个措辞哪个在真实使用上更好、审美保真度、跨会话输出稳定性——这些需要真实证据,交给 `~cultivate`。快速档不给这些打分,也不假装验证过。

一句话:**先用 `~tune` 把不需要数据就能修的都修掉(这通常已经让 skill 明显变好),需要数据的部分再决定要不要走深度档。** 这就是让这套系统有"day-1 价值"的关键——你不用等两周记日志才能开始。
