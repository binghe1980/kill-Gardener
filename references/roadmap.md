# Skill 未来方向引导(`~roadmap` 执行手册)

旧版只会修当前的失败,不会帮用户想"这个 skill 接下来该往哪走"。但一个 skill 用久了,真正的问题往往不是"某句措辞不好",而是**结构性的**:它是不是太大了该拆?某个能力是不是过时该废?是不是缺一块能力该长出来?是不是和另一个 skill 重了该合?

`~roadmap [skill]` 帮用户做这类**方向性决策**,而不只是打磨细节。它不改 skill,只产出一份带建议的方向评估。这是"未来发展方面的帮助"。

---

## 五类方向性决策

对一个 skill,依次问这五个问题。每个都给出判断信号和处理建议。

### 1. 该拆分吗?(Split)

**信号**:
- SKILL.md 明显过大(远超 500 行且靠堆功能撑大),或 description 里塞了多个不相关的触发场景
- 日志显示这个 skill 被用于差异很大的几类任务,每类的成功标准都不同(混合型里几个维度都 load-bearing 且互相拉扯)
- 用户经常只用它的一部分功能
- 同一个 skill 里,功能型的部分和创作型的部分要用完全不同的 rubric 评估(强信号)

**建议**:拆成 2-3 个聚焦 skill。每个有清晰单一意图、更准的触发、更短的正文。拆分后触发精度和可维护性都会提升。给出拆分方案草图(每个新 skill 的意图/触发/边界)。

### 2. 该废弃或收缩吗?(Deprecate / Shrink)

**信号**:
- 某能力依赖的外部条件已变(平台规则、API、工具改名、某模型下线)——对照 `~tune` 维度 4 的陈旧假设
- 日志显示某功能几乎不被触发,或每次触发都被用户否掉
- 这个能力现在被平台/工具原生支持了,skill 里的手工实现成了负担
- 整个 skill 的使用频率长期趋近于零

**建议**:废弃整个 skill,或收缩掉过时的部分。诚实告诉用户"这块现在没价值了,留着是维护负担"。收缩往往比新增更能提升 skill 质量(去掉噪声、降低规则疲劳)。

### 3. 该长出新能力吗?(Extend)

**信号**:
- 日志里反复出现用户想做、但当前 skill 不支持、只能手动补的事
- 与时俱进:领域出现了新的实用需求(如写作 skill 遇上平台新的投稿/合规要求;生成 skill 遇上新的翻车修复需求)
- 用户的后续追问总是同一类"能不能顺便也…"

**建议**:提出新增能力的方向和它该以什么形式进入(内联进主流程 / 新 reference 文件 / 新指令)。约束:新增不能稀释核心意图,不能违反篇幅纪律——常常要"加一块的同时删一块"。给出加什么、放哪、大概多大的草案。

### 4. 该和兄弟 skill 合并或分工吗?(Merge / Coordinate)

**信号**:
- 库里有 description 重叠的 skill,触发时会互相抢(A2 触发误发的根源之一)
- 两个 skill 经常被连着用,中间靠用户手动搬数据(如"改编 skill 产出剧本 → 视频 skill 吃剧本",结构对不上)
- 几个 skill 共享大段相同的方法论,各维护一份、容易漂移不一致

**建议**:
- **合并**:功能高度重叠的,合成一个,触发更清晰
- **分工划界**:功能相邻但各有价值的,明确各自边界 + 在 description 里互相"划清界限"(用 X 不用 Y),并打通交接格式(上游产出 = 下游期待的输入结构),形成流水线
- 抽公共方法论到共享 reference,各 skill 引用,避免漂移

### 5. 类型判断还对吗?(Reclassify)

**信号**:
- 用户对这个 skill 的在意点变了(以前只看对不对,现在开始在意风格/语气)——它可能从功能型漂成了混合型,评估方式该跟着变
- 一直当功能型优化,但用户总因"感觉不对"否掉输出(说明有未被承认的审美/创作维度)

**建议**:更新 manifest 的类型,相应调整评估方式(如新识别出审美维度 → 需要建锚点)。类型错了,后续所有优化都会用错 rubric。

## `~roadmap` 输出格式

```markdown
# <skill-name> 方向评估

## 一句话现状
[这个 skill 现在处于什么状态、健康吗、瓶颈在哪]

## 五类决策扫描
| 方向 | 判断 | 依据 | 建议 |
|---|---|---|---|
| 拆分 | 建议/不必 | [信号] | [方案草图或"暂不需要"] |
| 废弃/收缩 | 建议/不必 | [信号] | ... |
| 新增能力 | 建议/不必 | [信号] | ... |
| 合并/分工 | 建议/不必 | [信号] | ... |
| 重新分类 | 建议/不必 | [信号] | ... |

## 优先级建议
[如果只做一件事,先做哪个方向,为什么]

## 与 skill-creator 的分工
- 若建议"新建/拆出"新 skill → 交给 skill-creator(Anthropic 官方)从零搭
- 若建议"改进现有" → 回到 ~tune / ~cultivate
```

---

## 什么时候跑 `~roadmap`

- 一个 skill 已经 `~tune`/`~cultivate` 过几轮、细节问题都修得差不多,但用户感觉"还差点意思"时——往往是方向问题,不是细节问题
- 定期(如每季度)对整个 skill 库扫一遍,看有没有该拆、该废、该合的
- 用户明确问"这个 skill 接下来该怎么发展""我这套 skill 库该怎么规划"时

## 与 skill-creator 的关系(工作流分工)

- **skill-creator**(Anthropic 官方):从零**创建**新 skill、搭脚手架、跑 eval、优化 description 触发
- **skill-gardener**(本系统):**维护和演化存量** skill——诊断失败、静态审查(`~tune`)、经验证的深度培育(`~cultivate`)、健康追踪(`~health`)、方向规划(`~roadmap`)

两者互补:roadmap 建议"该拆出一个新 skill"时,把新 skill 的搭建交给 skill-creator;新 skill 用一段时间、积累了日志后,再纳入 gardener 培育。**创建归 creator,养护归 gardener。**
