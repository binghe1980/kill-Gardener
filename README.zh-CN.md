# Skill Gardener

> 一个面向 Claude Code Skill 的长期培育系统。  
> 成对偏好替代单一分数。真实日志替代合成 prompt。并行候选替代爬山迭代。风格锚点替代 rubric 形容词。

---

## 它做什么

Skill Gardener 通过以下方式帮你随时间演化 SKILL.md：

1. **记录 Skill 真实的使用场景**——不是你想象中的使用场景
2. **诊断具体失败**——基于一个经过设计的失败模式目录，每条诊断都有日志证据
3. **生成多个差异化的候选修复**——而不是一个凭经验的"改进方案"
4. **跑一场成对比较的锦标赛**——在你历史使用里抽取的真实 prompt 上
5. **在验证集上独立校验胜出者**——捕捉过拟合
6. **为审美/创作型 Skill 强制启用锚点门**——用你的参考样本把关，而不是形容词 rubric
7. **从每次成功优化中提炼跨 Skill 原则**——原则库随时间变聪明
8. **积累品味数据库**——用你的仲裁投票持续校准裁判

---

## 它不做什么

这里诚实比营销更重要：

- **它不会给出单一质量分数。** 这是刻意的。单一数字压缩多维权衡，邀请被游戏化。
- **它不会在没有证据的情况下优化 Skill。** 如果你既没有使用日志，又不愿提供锚点或回溯数据，系统会拒绝执行——它不会凭空编造"改进"。
- **它不保证每次都能改进。** 有时候没有候选能通过验证集。这种情况下系统会如实告诉你，而不是硬塞一个可疑的修改。
- **它不是魔法。** 优化质量的上限由你的日志质量、锚点质量、反馈质量决定。Garbage in, garbage out 依然成立。
- **它不假装子 agent 评估是真独立。** Claude 评判 Claude 的输出有已知偏差。协议能缓解一部分，用户仲裁补齐剩下一部分。

如果你想要的是一键"让我的 Skill 变得更好"，这不是它。如果你想要的是一个陪你长期打磨、几个月几年之后逐渐积累真知识的系统，从这里开始。

## 核心设计选择

### 成对偏好，非绝对评分

LLM 裁判给绝对分（78 还是 82？85？）时极不稳定，但做成对选择时相对稳定。竞技场完全使用成对比较。输出是：胜负场次、理由、置信区间——不是"这个 Skill 现在 87/100 分"。

### 真实调用，非合成 prompt

两三条凭想象写的测试 prompt 无法代表真实使用分布。Skill Gardener 使用你实际的 Skill 调用日志（被动收集）作为评估集，按训练 / 验证集拆分。合成 prompt 只作为冷启动兜底，且会被标记为低置信度。

### 并行候选，非单点迭代

每一轮从不同策略类别——tighten / demonstrate / remove / reorder / decompose / scaffold / reframe / rewrite——生成 4-6 个候选。它们在锦标赛中对决。这是逼近"进化"的唯一方式；单候选逐轮迭代只是爬山。

### 锚点，非 rubric 形容词

"温暖、精致、权威"对审美型 Skill 不是一份规格。参考样本才是。对任何审美或创作型 Skill，系统要求 5-10 个正向锚点、3-5 个负向锚点。它们会在冠军敲定前门栏每一个候选。

### 按类型分流

功能型、审美型、创作型 Skill 的失败模式和成功标准都不同。循环会根据 Skill 类型自适应调整。一套 rubric 通吃所有类型，会悄悄损伤那些和 rubric 隐含假设不一致的 Skill 类别。

### 原则跨 Skill 传递

当一次优化成功时，系统提炼一条通用原则——例如："对声称口语化语气的 Skill，few-shot 示例比禁用词清单有效"。这些原则积累进一个库，会被用到未来其他 Skill 的候选生成中。今天优化的 Skill 让明天的 Skill 优化更好。

### 品味数据库作为长期资产

你投下的每一票仲裁都会被记录。随着时间推移，它成为**你个人的校准档**——你审美判断的高保真数字化。可携带、可审计、使用越久越有价值。

## 安装

```bash
# 把 skill-gardener 文件夹克隆或复制到你的 Claude Code Skills 目录
cp -r skill-gardener ~/.claude/skills/
```

首次调用时会初始化运行时状态（`_runtime/` 文件夹下的日志、原则库、品味数据库）。

---

## 基础用法

```
# 首次：分类你的 Skill，设置日志
"帮我配置 skill-gardener"

# 诊断但不改
"诊断我的 landing-page Skill"

# 完整培育循环
"培育我的 landing-page Skill"

# 审美/创作型 Skill：先建锚点
"给我的 landing-page Skill 建锚点"

# 查看积累
"显示原则库"
"显示我的品味数据库"
"显示培育历史"
```

自然语言全流程可用。熟练用户可用短命令（`~cultivate`、`~diagnose`、`~anchor`、`~log`、`~principles`、`~taste`、`~review`），效果等价。

## 适用场景

**合适的场景：**

- 你有 5 个以上长期使用的 Skill，想做长期维护
- 你有一批历史 Skill 输出可用作锚点或回溯日志
- 你愿意为每个 Skill 花 15-30 分钟做培育的前置配置
- 你在乎质量，愿意审核险胜决策而不是全自动接受
- 你希望你的 Skill 维护实践随着月份沉淀成知识

**不合适的场景：**

- 你只有一两个偶尔用的 Skill
- 你想要一个无人看守的一次性优化器
- 你不愿为审美型 Skill 建锚点——系统不会假装已经优化过
- 你期望得到一个"总评分"作为输出
- 你没有使用数据、没有参考样本，还希望它工作

## 架构概览

```
skill-gardener/
├── SKILL.md                       # 入口——培育流程总调度
├── README.md                      # 本文件
└── references/
    ├── skill-types.md             # 功能/审美/创作/混合型分类 + manifest 格式
    ├── failure-modes.md           # 失败模式目录 + 检测启发
    ├── candidate-strategies.md    # 按失败模式组织的改进策略菜单
    ├── arena-protocol.md          # 成对比较和裁判 agent 协议
    └── anchor-system.md           # 风格锚点的建立与维护
```

运行时状态（生成，不随包发布）：

```
_runtime/
├── principles.md                  # 随时间积累的跨 Skill 原则
├── taste-db.jsonl                 # 每行一票用户偏好
├── skill-registry.yaml            # Skill 分类和 manifest 路径
└── logs/<skill-name>/
    ├── usage.jsonl                # 被动使用日志
    └── cultivation-<timestamp>/   # 每轮培育一个文件夹
        ├── diagnosis.md
        ├── candidates/
        ├── arena-results.md
        ├── holdout-results.md
        └── outcome.md
```

## 诚实的局限

上面的设计部分提过这些，这里明文再列一遍：

- **子 agent 的独立性是近似的。** 同模型家族、同训练。竞技场协议可以一定程度上对抗位置偏差、长度偏差、自我偏好，但不能消除所有 Claude 家族模型都共有的系统性偏差。主要靠用户仲裁来兜底。

- **日志采集需要配套工程。** Claude Code 原生不会把所有 Skill 调用自动记录成结构化日志。你需要（a）重要会话后手动追加到 `_runtime/logs/<skill-name>/usage.jsonl`，或（b）依赖回溯/冷启动模式。未来版本可能加入会话钩子实现自动记录。

- **计算成本是真的。** 对单个 Skill 完整跑一轮培育，涉及 4-6 次候选生成、300+ 次竞技场判断、锚点把关、验证集校验。对大型 Skill 库要做成本预算。可以用 `~cultivate --fast` 预算感知模式，以置信度换速度。

- **原则可能是错的。** 从某次成功优化里提炼的原则不一定能泛化。原则库需要定期审阅，对误导过系统的原则要标记为废弃。

- **冷启动模式确实更差。** 如果没日志没锚点没回溯数据就跑，系统会退回到 Claude 生成测试 prompt 的模式。它能跑但结果置信度低——不要假装置信度比你实际拥有的更高。

## 写在最后

Skill 是长期资产，它们不受益于突发式的一次性优化，而受益于耐心的观察和有原则的调整。如果你想要的是"一个下午让 Skill 脱胎换骨"，这不是它。如果你想要的是"一个随时间把你的 Skill 库默默变得更可靠、同时教会你关于自己品味的东西"的系统——就是它。

欢迎贡献。如果你遇到的失败模式不在目录里，提 issue 尤其欢迎。
